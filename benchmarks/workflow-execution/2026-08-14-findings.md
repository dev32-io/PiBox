# Workflow Execution Benchmark Findings — 2026-08-14

## Scope

The first durable execution benchmark covered:

- mixed serial and parallel scheduling;
- resource-claim serialization;
- failure pause and explicit resume;
- review/fix/re-review and residual-risk checkpoints;
- atomic parallel merge conflict rollback;
- post-merge check rollback;
- dirty canonical work preservation;
- interrupted-run recovery;
- durable worker change requests and same-agent resumed attempts;
- routine real-model workflow execution;
- targeted `task_clarify` behavior;
- worker-discovered task/spec contradictions and orchestrator judgment.

All real-model runs used `openai-codex/gpt-5.6-luna#medium` for the main session and managed agents.

## Results

- Deterministic suite: **100/100**, 12/12 passed after adding final-journey deduplication coverage.
- Model aggregate: **91/100**, 1/3 scenarios passed dimension gates.
- Routine model workflow: **90**, failed protocol gate.
- Targeted clarification: **95**, passed.
- Worker change request: **87**, failed autonomy gate.

A successful final outcome cannot override a failed critical dimension. Outcome, safety, verification, and clarification require 100; protocol requires at least 50; autonomy requires at least 75.

## Fixes applied

These were local, non-policy defects:

1. Model subprocesses now launch with ignored stdin; the former `execFile` pipe could leave print-mode Pi waiting before its first tool call.
2. Model supervision allows enough reconciliation turns and explicitly detects settled gates before requesting completion.
3. Transcript metrics count each tool once and retain failed lifecycle calls as protocol violations.
4. `task_complete.commits` and the managed-task prompt explicitly require full 40-character commit SHAs.
5. Completion prompts and `work_item_complete` now require the bare work-item ID.
6. Completion guidance explains that `outcome.md` is normally created by the completion gate; pre-gate absence is not a deviation.
7. Aggregate model scoring now includes user-escalation metrics and non-negotiable dimension gates.

## Successful behavior

- A complete routine ticket caused zero `task_clarify` calls.
- A deliberately incomplete ticket caused exactly one direct read of the relevant specification and no broad listing.
- An impossible task caused the implementer to read the relevant specification, submit a precise blocking change request, stop safely, and preserve clean state.
- After explicit steering, one atomic `workflow_apply_change` amended the task, responded durably, reused the same logical agent in a fresh attempt, and resumed execution.
- Merge conflicts and failing post-stage checks restored the exact pre-stage feature commit while preserving contribution branches/worktrees.
- All completed model fixtures retained passing task checks, E2E evidence, final review, clean Git state, and an accurate branch handoff.

## Critical finding — unresolved authority precedence

The worker change-request scenario intentionally made a task require both:

- omission of stable `id` from serialized data; and
- exact identity restoration without any alternate channel.

The canonical intent and specification explicitly required identity preservation and said omission without another durable channel violated the product contract. The orchestrator read the intent, specification, and task, but still asked the user to choose. It did not infer that the lower-level task was the contradictory resource and amend it back to the settled higher-level contract.

This is a real long-running-autonomy weakness. However, broadly teaching the orchestrator to rewrite tasks whenever they conflict with higher artifacts could override an intentionally reviewed exception. Because this changes user-authority policy, no fix was applied.

Options for discussion:

1. Define intent/spec/design as higher authority unless a task explicitly records an approved deviation.
2. Add a structured task-level `supersedes` or approved-deviation marker.
3. Permit autonomous amendment only when it narrows a task back to unambiguous higher-level acceptance without changing observable behavior.
4. Extend change requests with affected resource refs and a proposed contract delta.

## Resolved after review — duplicate final journey gates

The initial run showed that a plan containing an explicit whole-branch journey evaluation still received the harness-owned `final-e2e`, because startup checked only fixed IDs. After reviewing the intended development flow, the boundary is now:

- delivery planning owns focused deterministic, regression, migration, and independent review evaluations;
- runtime owns the final whole-branch journey and final branch review;
- the planner skill no longer mentions or demonstrates E2E evaluation authoring;
- public planner evaluation authoring rejects new `e2e` evaluations;
- legacy plans remain readable;
- startup semantically adopts an existing work-item-scoped E2E or `final-e2e` checkpoint instead of inserting a duplicate;
- final branch review depends on the actual adopted journey evaluation rather than a fixed ID.

The deterministic `final-journey-dedup` scenario and focused store/adapter tests now enforce this behavior. A future Luna baseline rerun should show one fewer evaluator process for fixtures that previously planned an overlapping gate.

## Protocol observations

Luna occasionally supplied an incorrect full commit SHA to `task_complete`, was rejected, then corrected itself. Deterministic validation worked as intended. One such retry remains acceptable under the current protocol threshold; repeated retries fail the scenario.
